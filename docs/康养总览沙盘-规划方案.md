## 一、目标与非目标

### 目标

做一个**独立的"总览沙盘"页面**，把整个康养园区的三维空间呈现在一个场景里：园区 → 楼栋 → 楼层 → 房间 → 设备，层级逐级下钻；房间按实时数据着色，形成"看得见态势"的数字孪生总览。

保留现有的**单主题特写模式**（居室/走廊/餐厅/护理站/康复室五个场景），两者互相切换：沙盘是汇总入口，点进去才到单场景。

### 非目标（本期明确不做）

| 不做 | 原因 |
|---|---|
| 引入外部 GLTF 建筑模型 | 无建模方、包体会涨 10–50 倍、与现有发光风格违和、GLTF 的 node 拆名是可点击性的硬约束且无人承担 |
| 更换现有视觉风格 | 沿用「暗色 + 橙色发光 + 玻璃面板」，保证与现有 9 个页面同源统一 |
| 按房型做 4 套室内模板 | 本期所有卧室统一复用现有「居室」主题，房型细分留到后续 |
| 改造现有 `Dashboard.vue` / `Room3D.vue` | 红线：不能改崩现有系统。`Room3D` 仅作为「房间内部渲染器」被复用 |

## 二、架构核心：数据驱动的空间树

这是整个方案的地基。因为后续要加房型、加楼层、加室外、加多栋建筑，**绝不能把建筑结构写死在代码里**。

```
space_nodes（单表自引用树）
  campus    园区
  └ building 楼栋
      └ floor 楼层
          ├ room 房间（关联 rooms.id）
          └ zone 功能区（走廊 / 餐厅 / 护理站 / 康复室）
```

新增楼栋 = 插一行 `building`；新增楼层 = 插一行 `floor`；调整布局 = 改 `x/z/width/depth`。
**三维生成器只负责遍历这棵树，代码零改动。** 这是"方便后期拓展"的落地方式。

### 表结构（新增，零侵入）

```sql
CREATE TABLE IF NOT EXISTS space_nodes (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  code        TEXT UNIQUE NOT NULL,   -- 空间编码：CAMPUS-1 / B1 / B1-F1 / 101
  name        TEXT NOT NULL,          -- 显示名：康养园区 / 1号楼 / 1层 / 101室
  node_type   TEXT NOT NULL,          -- campus | building | floor | room | zone
  parent_code TEXT,                   -- 自引用（用 code 而非 id，方便人工维护配置）
  room_id     INTEGER,                -- node_type=room 时关联 rooms.id
  -- 空间几何（单位：米）
  x           REAL DEFAULT 0,
  z           REAL DEFAULT 0,
  y           REAL DEFAULT 0,         -- 楼层高度偏移
  width       REAL DEFAULT 0,         -- 沿 X 轴
  depth       REAL DEFAULT 0,         -- 沿 Z 轴
  height      REAL DEFAULT 3.2,
  rotation    REAL DEFAULT 0,
  -- 扩展位与展示
  sort        INTEGER DEFAULT 0,
  meta        TEXT DEFAULT '{}',      -- JSON：门宽、朝向、房型、渲染样式等
  created_at  TEXT DEFAULT (datetime('now','localtime'))
);
```

**为什么用自引用单表而不是分层建表**：加一层抽象（比如"园区里的区域"）不用改表结构；查询一次全量树在前端组装，18 个节点量级，性能无压力。`meta` JSON 字段是留给未来的扩展位（比如给某类房间挂自定义渲染参数）。

## 三、建筑模数（依据 JGJ 450-2018）

按《老年人照料设施建筑设计标准》取值，**1 个三维单位 = 1 米**。

| 参数 | 取值 | 规范依据 |
|---|---|---|
| 双人间居室 | 4.0 × 4.0 = **16 ㎡** | 双人间使用面积 ≥ 16.00 ㎡ |
| 走廊通行净宽 | **2.4 m** | 通行净宽 ≥ 1.80 m |
| 层高 | **3.2 m** | 老年设施常用 3.0–3.6 m |
| 楼板厚 / 隔墙厚 | 0.3 / 0.2 m | — |
| 护理型房间门宽 | **1.1 m** | 护理型床位居室门 ≥ 1.10 m |
| 普通房间门宽 | 0.9 m | ≥ 0.8 m，宜 ≥0.9 m |

**合规性**：每层 6 间 × 2 床 = 12 床，3 层共 **36 床 ≤ 60 床/照料单元** ✓

### 默认楼层平面（对称鱼骨形）

```
        ┌──────┬──────┬──────┐
        │ 101  │ 102  │ 103  │
        ├──────┴──────┴──────┤         ┌────────┐
        │    走廊  2.4m       │─────────│  护理站 │
        ├──────┬──────┬──────┤         └────────┘
        │ 104  │ 105  │ 106  │
        └──────┴──────┴──────┘
        ←──────── 12m ────────→   端头 3m
        楼层整体 15m × 10.4m
```

- 每层：6 间房（南北各 3 间） + 走廊 + 端头护理站
- 整栋：15 × 10.4 × 9.6 m（3 层）
- 1 层端头额外布置：餐厅、康复室

> 布局**全部写在 `space_nodes` 表里**，不满意直接改数据即可，不用改代码。南北朝向差异在沙盘视角下不做区分，仅在 `meta` 里标记朝向。

## 四、必须前置解决的数据问题（P0）

### 问题：房间编号体系不一致

| 表 | `room_no` 取值 | 与 `rooms` 能否关联 |
|---|---|---|
| `rooms` | `101` … `306`（3 位） | — |
| `devices` / `device_usage` / `room_environment` | `101` … `306` | ✅ 可关联 |
| **`residents`** | **`1011` `1012` … `1052`（4 位）** | ❌ **0/10** |
| **`alarms`** | **`1011` … `1052`（4 位）** | ❌ **0/10** |

**根因**：`1011` 的编码是 `{房号3位}{床位1位}`（1011 = 101 房 1 床）。而 `rooms.room_no` 只有房号，没有床位维度。两套编码从未建立关联。

**这就是 `Dashboard.vue:341` 把所有住户硬编码成 `district: '101室'` 的原因** —— 不硬编码，一个都对不上。

**影响**：不改的话，沙盘**无法做到"哪间房有告警就变红"**，因为告警与房间 JOIN 不上。

### 处理方案

1. **规范化 `residents.room_no` / `alarms.room_no` 到 3 位房号**（取前 3 位），床位号另存（新增 `bed_no` 字段），与 `rooms.capacity = 2` 对齐。
2. **重建一套自洽的演示数据**：让 18 间房 / 36 床 / 住户 / 告警 / 设备 / 环境全部按真实房号互相对齐，且分布在 3 层（现在住户全挤在 1 楼 5 间房里，2、3 楼是空的，沙盘上会难看且不真实）。
3. **新增「按房间聚合」接口**：`GET /api/overview/rooms` → 每间房的 `{ room_no, floor, occupancy, deviceOnline, pendingAlarms, worstHealth, status }`，供沙盘着色使用。
4. **顺手修掉 `Dashboard.vue:341`** 的 `101室` 硬编码，改为真实房间号。

> ⚠️ **这是本方案唯一触及现有数据/现有文件的环节**，需要你明确批准。
> 回滚保障：改动前备份 `server/data/kangyang.db`；迁移脚本单独成文件，可反向执行。

## 五、前端结构（全部新增，零侵入）

```
src/
├── views/
│   └── Overview.vue              【新】总览沙盘页面（新路由 /overview）
├── components/
│   ├── Campus3D.vue              【新】园区沙盘渲染器（楼栋/楼层/房间外壳 + 相机）
│   ├── RoomDetailPanel.vue       【新】选中房间后的数据面板
│   └── Room3D.vue                【复用·不改】房间内部渲染器
├── composables/
│   └── useSpaceTree.js           【新】读取 space_nodes 并组装成树
└── api/index.js                  【改】仅新增两个接口函数，不动现有函数
```

### 两个渲染器的职责边界

| 渲染器 | 负责 | 相机 |
|---|---|---|
| `Campus3D.vue`（新） | 整栋楼外壳、楼层、房间色块、功能区外形 | 围绕**可变聚焦目标**的轨道相机 |
| `Room3D.vue`（复用） | 房间内部（床、监护仪、护理站大屏等） | 保持现有实现不动 |

**关键点**：`Room3D.vue` 本来就是 `props.theme` 驱动的纯展示组件，天然可复用，**一行都不用改**。

### 相机设计

现有 `Room3D.vue` 的相机是"绕原点转盘"（`lookAt(0,3,0)` 写死、半径限位 18–65）。
`Campus3D.vue` 采用**可变聚焦目标**：

- **L1 全楼**：目标 = 建筑中心，半径 ≈ 26，可见整栋（建筑 15×10.4×9.6m）
- **L2 聚焦房间**：点房间后，目标平滑过渡到该房间中心，半径收缩到 ≈ 6
- **复位**：一键回到 L1

按真实尺度建模后建筑仅 15m 长，**现有 18–65 的半径限位完全够用**（此前"融合后跨度 60–100 单位"的判断经复核是错的，已修正）。

### 视觉与 LOD

| 层级 | 呈现 |
|---|---|
| L1 全楼 | 楼体**半透明外壳** + 内部房间状态色块（正常/关注/紧急/空闲四色）+ 悬浮数据标签；可点"分层高亮"单独突出某一层 |
| L2 房间 | 相机推近 + 右侧滑出 `RoomDetailPanel`（住户、健康指标、设备、未闭环告警） |
| L3 内部 | 面板上点「进入房间」→ 挂载 `Room3D` 渲染居室内部，复用现有五个主题 |

**功能区**（走廊/餐厅/护理站/康复室）在 L1 以独立色块呈现，点击后同样可进入对应的现有主题。
