# 康养数字孪生 · Three.js 模型重构规划

> 状态：**规划完成，待分阶段实施**  
> 制定日期：2026-09-29  
> 线上基线：http://152.136.36.198/overview  
> 目标：保留“园区总览沙盘 + 单主题特写”双模式，去掉无业务意义的装饰粒子，引入适合康养主题的人物与设施模型，并统一操作手感。

---

## 一、先给结论

### 1. 粒子：可以去，而且建议直接去

当前粒子只出现在 `src/components/Room3D.vue`：

- `createParticles(theme, 60)` 创建 60 个随机漂浮点；
- 每帧旋转并逐点修改 Y 坐标；
- 不绑定住户、告警、设备或环境数据；
- `Campus3D.vue` 的园区总览没有这套粒子。

因此移除它不会影响：

- 房间、设备、住户点击；
- 告警状态与房间着色；
- 总览沙盘；
- 房间下钻；
- 选中光环、告警呼吸或数据面板。

建议保留“有业务意义的动效”，去掉“纯装饰漂浮点”：

| 动效 | 处理建议 | 原因 |
|---|---|---|
| 随机漂浮粒子 | **删除** | 容易形成科幻演示感，不符合真实康养院主题 |
| 紧急房间呼吸提示 | 保留，但降低频率 | 表达告警优先级，有业务含义 |
| 选中房间描边/光环 | 保留并减弱光柱 | 帮助确认当前选中对象 |
| 设备在线脉冲 | 后期按真实在线状态启用 | 数据驱动，不做无意义循环 |
| 人物待机/走动 | 新增 | 符合真实运营场景 |

### 2. 人物骨架：做“骨骼绑定人物”，不做“可见骨骼线”

用户看到的应该是康养院人物，而不是开发调试骨架。

推荐人物类型：

1. **老人·步行**：站立、缓慢行走、坐下、起身；
2. **老人·辅具**：拐杖、助行器；
3. **老人·轮椅**：坐姿、轮椅缓慢移动；
4. **护理员**：站立、巡房、记录、搀扶；
5. **访客**：后期扩展，不作为第一阶段重点。

技术上使用 GLB/GLTF 的 `SkinnedMesh + Skeleton + AnimationMixer`。`SkeletonHelper` 只在开发模式下用于检查关节，不进入正式界面。

### 3. 不把总览沙盘强行改成写实建筑

`Campus3D` 当前的“半透明建筑 + 房间状态色块”适合回答：

- 哪层有问题？
- 哪间房紧急？
- 哪间房空闲？
- 点击后从哪里下钻？

总览层如果塞入床、桌椅、人物五官，会导致：

- 房态颜色被模型遮挡；
- 三层叠加后信息密度失控；
- 移动端性能下降；
- 用户更难选中房间。

所以应保持三级模型精度：

```text
L0 园区/楼栋总览：抽象状态模型，强调态势
L1 楼层/功能区：墙、门、走廊、房间边界，强调空间关系
L2 房间/主题特写：家具、设备、人物动画，强调真实细节
```

## 二、当前模型为什么“看起来和操作起来有点别扭”

## 2.1 两套相机控制逻辑不一致

### Room3D

当前特点：

- 相机固定 `lookAt(0, 3, 0)`；
- 水平拖拽修改 `orbitAngle`；
- 垂直拖拽修改 `orbitHeight`；
- 不是围绕当前选中对象的真实球面轨道；
- 选中对象后只显示光环，没有把相机焦点平滑移动过去；
- 主题场景尺寸差异很大，但共用半径 `18–65`。

后果：

- 用户上下拖动时感觉像“升降机”，不是正常俯仰；
- 点击床、老人或设备后，镜头仍看向原点；
- 居室、走廊、康复室的最佳观察距离不同，但控制参数相同；
- 下钻到具体房间后虽然数据过滤正确，镜头表达仍是一个通用舞台。

### Campus3D

当前特点：

- 已使用可变焦点 `target / goalTarget` 和阻尼；
- 但仍是自写手势系统；
- 只能旋转和缩放，不能平移；
- 透明楼层叠加时，射线可能先命中近侧房间；
- 用户只能在 3D 画面里“猜着点”，没有与房间列表双向联动。

### 统一方向

新增统一的 `useSceneControls`：

```text
桌面端
- 左键拖拽：旋转
- 滚轮：缩放
- 右键/中键拖拽：平移（可选）
- 单击：选中
- 双击：进入/下钻
- Esc：退出选中或回上一级
- R / 首页按钮：重置视角

触控端
- 单指拖拽：旋转
- 双指捏合：缩放
- 双指同向移动：平移
- 轻点：选中
- 再点“进入”：下钻，避免误触直接跳转
```

统一参数：

- 旋转、缩放使用阻尼；
- 目标点、距离、方位角、俯仰角都走同一套插值；
- 每类场景配置自己的 `cameraPreset`；
- 聚焦对象时保留周围上下文，不把镜头贴到模型表面；
- `prefers-reduced-motion` 下关闭自动呼吸和长过渡。

## 2.2 当前单主题模型更像“示意舞台”，不是实际房间

`Room3D.vue` 内部是一个超过千行的单文件程序化模型：

- 居室墙面约 20m × 16m；
- 走廊约 6m × 24m；
- 餐厅、护理站、康复室各自用 Box/Cylinder 等基础几何体搭建；
- 五个主题共用 48m × 36m 地面；
- 全部在原点附近生成；
- 没有外部 GLB/GLTF 模型资产。

这与总览数据里的真实模数不一致：

- 双人间：4m × 4m；
- 走廊净宽：2.4m；
- 层高：3.2m。

因此不能继续在 `Room3D.vue` 里无限追加几何体。否则后期增加卫生间、门窗、适老家具、轮椅、护理床、人物和动画后，会迅速变成不可维护的巨型组件。

## 三、目标架构

## 3.1 场景编排层

建议将现有两个渲染器逐步拆成：

```text
src/three/
├─ core/
│  ├─ SceneRuntime.js          # renderer / scene / camera / 生命周期
│  ├─ SceneControls.js         # 统一鼠标与触控操作
│  ├─ AssetLoader.js           # GLB/纹理加载、缓存、错误回退
│  ├─ MaterialLibrary.js       # 康养统一材质语言
│  ├─ Picker.js                # 射线拾取与命中优先级
│  └─ PerformanceMonitor.js    # FPS / draw call / triangles
├─ manifests/
│  ├─ models.js                # 模型注册表
│  ├─ characters.js            # 人物角色、动画、LOD
│  └─ scenes.js                # 场景与相机预设
├─ scenes/
│  ├─ CampusScene.js           # 园区/楼栋态势
│  ├─ FloorScene.js            # 单层空间
│  └─ RoomScene.js             # 房间/功能区特写
├─ builders/
│  ├─ RoomShellBuilder.js      # 墙、门、窗、地面
│  ├─ FurnitureBuilder.js      # 床、柜、桌椅等布置
│  ├─ DeviceBuilder.js         # IoT 设备
│  └─ CharacterBuilder.js      # 人物生成与状态绑定
└─ systems/
   ├─ CharacterSystem.js       # 动画状态机
   ├─ AlarmVisualSystem.js     # 告警视觉
   ├─ LabelSystem.js           # 标签分级显示
   └─ NavigationSystem.js      # 人物路径与站位点
```

Vue 组件只负责：

- 传入节点、房态、住户和设备数据；
- 接收 select / enter / back 事件；
- 显示数据面板；
- 不再直接承载所有 Three.js 建模代码。

## 3.2 模型注册表

新增数据驱动的模型注册表，而不是在场景里到处写 URL、比例和坐标：

```js
{
  id: 'character-resident-walker',
  url: '/assets/models/characters/resident-walker.glb',
  category: 'character',
  roles: ['resident'],
  scale: 1,
  animations: {
    idle: 'Idle',
    walk: 'WalkSlow',
    sit: 'Sit',
    stand: 'StandUp'
  },
  lod: {
    high: 12,
    medium: 28,
    proxy: 45
  },
  budget: {
    triangles: 25000,
    fileSizeKB: 1200
  }
}
```

收益：

- 换模型不改场景代码；
- 可以记录授权来源；
- 统一比例、朝向、动画名；
- 可按距离切换 LOD；
- 后期增加楼栋或房型，只增加清单与布局数据。

## 3.3 资产加载

使用 Three.js 官方加载链：

- `GLTFLoader`：加载 GLB/GLTF；
- `DRACOLoader` 或 Meshopt：压缩几何体；
- `KTX2Loader`：压缩纹理；
- `SkeletonUtils.clone()`：复用同一个人物模型的骨骼资源；
- 全局 Promise 缓存：同一资产只请求和解析一次；
- 加载失败时退回程序化代理人形，不让场景空白。

所有模型存本地：

```text
public/assets/models/
├─ architecture/
├─ furniture/
├─ medical/
├─ devices/
├─ characters/
└─ licenses/
```

不在运行时引用不稳定的第三方模型 URL。

## 四、人物系统设计

## 4.1 两种显示精度

### 园区/楼层总览：简化人物代理

总览不需要五官和衣服褶皱，使用：

- `InstancedMesh` 人形剪影或胶囊人；
- 颜色表示角色或健康状态；
- 只在选中楼层、拉近视角时显示；
- 远景只显示人数和房间状态，不显示 10 个小人穿墙叠在一起。

建议规则：

```text
全楼视角：不显示人物，只显示房态和人数
单层视角：显示简化人物/站位点
房间视角：显示完整骨骼人物
```

### 房间/功能区特写：骨骼人物

每个可见场景控制在 2–8 个动画人物：

- 居室：卧床或坐姿老人 + 护理员；
- 走廊：步行老人、轮椅老人、巡房护理员；
- 餐厅：坐姿老人 + 配餐护理员；
- 护理站：值班护理员；
- 康复室：老人扶平行杠训练 + 康复师。

## 4.2 人物状态机

人物动画不能随机乱走，应由业务状态驱动：

```text
ResidentState
- idle_stand
- idle_sit
- rest_bed
- walk_slow
- wheelchair
- rehab_training
- needs_attention

NurseState
- desk_work
- patrol
- inspect_device
- assist_resident
- alarm_response
```

数据映射示例：

| 业务数据 | 3D 表现 |
|---|---|
| 住户在住且稳定 | 坐姿/休息，低频待机动画 |
| 健康关注 | 黄色状态环，不改变人物肤色或衣服 |
| 紧急告警 | 红色房间提示 + 护理员响应路径 |
| PIR 活动 | 在允许区域内缓慢移动 |
| 跌倒告警 | 不播放夸张跌倒循环；显示一次姿态 + 告警标记 |
| 空房 | 不生成人物 |

## 4.3 路径与碰撞

第一阶段不引入重型物理引擎，使用“导航锚点 + 路径段”：

```text
room.entry
room.bed.1
room.bed.2
room.window
corridor.waypoint.1
nurse.station
rehab.parallelBars
```

人物只在合法锚点之间移动，避免：

- 穿墙；
- 穿床；
- 从楼板掉下；
- 轮椅转进不可能通过的狭窄区域。

后期园区规模变大，再评估 NavMesh；当前框架阶段没必要先上物理引擎。

## 五、符合康养主题的模型清单

## P0：必须先建立的空间模型

- 4m × 4m 双人居室外壳；
- 1.1m 护理型门；
- 2.4m 走廊；
- 门、窗、踢脚线、扶手；
- 房间锚点、入口锚点、床位锚点；
- 墙体透明/剖切模式。

## P1：核心适老家具

- 护理床、床头柜、衣柜；
- 扶手椅、适老餐桌椅；
- 防滑地面与夜间地脚灯；
- 卫生间扶手、紧急呼叫按钮；
- 轮椅、助行器、拐杖。

## P2：核心业务设备

- 心率/血氧监测设备；
- 床垫传感器；
- 跌倒/PIR 传感器；
- 智能手环；
- 呼叫器；
- 温湿度与空气质量传感器；
- 护士站终端。

## P3：人物与动画

- 老人：站、坐、卧、缓慢行走；
- 轮椅老人；
- 护理员：站、巡房、记录、搀扶；
- 康复师：指导平行杠训练。

## P4：园区扩展

- 大门、道路、花园、停车区；
- 室外座椅、无障碍坡道；
- 第二栋楼与建筑分区；
- 室外气象和环境设备。

## 六、视觉方向

主题应从“科幻模型展示”调整为“温暖、可信、可读的康养数字孪生”。

### 保留

- 深色大屏基底；
- 橙色品牌主色；
- 红/黄/绿/灰房态；
- 半透明建筑剖视；
- 清晰的楼层和房号标签。

### 减少

- 漂浮粒子；
- 过强自发光；
- 长光柱；
- 所有对象都金属化；
- 过度脉冲和随机动画。

### 新增

- 室内暖白光与日照方向；
- 木色、暖灰、浅绿等康养材质；
- 人物柔和轮廓；
- 真实的门宽、床位、扶手和轮椅通行关系；
- 数据状态环、路径线、设备小标记等“有业务含义”的视觉。

## 七、性能预算

## 7.1 总览沙盘

| 指标 | 桌面目标 | 手机目标 |
|---|---:|---:|
| 首次可交互 | ≤ 5s（常规公网） | ≤ 8s |
| Draw Calls | ≤ 120 | ≤ 80 |
| 可见三角面 | ≤ 250k | ≤ 120k |
| 动画人物 | 0–8 | 0–3 |
| 像素比 | ≤ 2 | ≤ 1.5 |

## 7.2 房间特写

| 指标 | 目标 |
|---|---:|
| 单个人物模型 | 15k–30k 三角面 |
| 单个人物压缩体积 | ≤ 1.5MB |
| 单场景人物 | 2–8 个 |
| 同时播放动画 | ≤ 6 个 |
| 单张纹理 | 优先 1024，必要时 2048 |
| 完整特写场景 | 压缩后建议 ≤ 8MB |

优化顺序：

1. 复用材质与几何体；
2. 静态家具合批；
3. 远景人物用代理或 InstancedMesh；
4. GLB 使用 Meshopt/Draco；
5. 纹理使用 KTX2/WebP；
6. 标签按距离分级显示；
7. 不可见楼层停止人物动画更新；
8. 页面不可见时暂停渲染循环。

## 八、分阶段实施路线

## M0：去装饰粒子 + 建立性能基线

改动：

- 删除 `Room3D` 粒子创建、更新与清理逻辑；
- 保留数据驱动的紧急呼吸和选中提示；
- 记录五个主题的 draw call、三角面、FPS；
- 不改变场景几何和数据接口。

验收：

- 五主题与总览都能打开；
- 点击、拖拽、缩放无回归；
- 控制台错误 0；
- 现有 10 路由冒烟通过。

风险：低。建议作为下一次实施的第一步。

## M1：统一相机与操作

改动：

- 抽出 `SceneControls`；
- Room3D 从固定 `lookAt(0,3,0)` 改为可变焦点；
- 加阻尼、统一拖拽阈值、统一重置；
- 房间列表/数据面板与 3D 选中双向联动；
- 增加场景路径面包屑：园区 > 1号楼 > 1层 > 101室。

验收：

- 两个模式操作一致；
- 旋转不误选，点击不误拖；
- 聚焦后仍能看到周边上下文；
- 手机双指缩放不跳变。

风险：中。先单独交付，不与人物同时开发。

## M2：模型架构拆分 + 房间真实模数

改动：

- 建立 `src/three` 核心层；
- 将居室按 4m × 4m 重建；
- 走廊按 2.4m 重建；
- 增加墙/门/窗/床位锚点；
- `Room3D.vue` 退化成薄组件，不再容纳全部模型代码。

验收：

- 空间尺度与 `space_nodes` 一致；
- 101/护理型房间可按房型模板生成；
- 点击房间下钻后，房间号、住户和床位一致；
- 旧主题入口继续可用。

风险：中高。必须保留现有渲染器作为 feature flag 回退。

## M3：人物代理 + 骨骼人物 MVP

改动：

- 先做 3 个角色：步行老人、轮椅老人、护理员；
- 每个角色先接 idle/walk/sit 三类基础动画；
- 总览使用人物代理，特写使用骨骼人物；
- 从住户和房间数据生成角色；
- 空房不生成人物。

验收：

- 人物不穿墙、不穿床；
- 101 室两位住户只出现两个人物；
- 轮椅与走廊/门宽关系可读；
- 移动端可自动降级成人形代理。

风险：中高。模型资产和动画质量决定最终观感。

## M4：康养业务动画

改动：

- 护理员巡房；
- 老人康复训练；
- 告警响应路径；
- 设备在线状态；
- 环境异常提示；
- 角色标签与数据卡片。

验收：

- 动画全部由数据或明确演示脚本触发；
- 无随机乱走；
- 告警动作可暂停；
- `prefers-reduced-motion` 生效。

风险：中。重点防止“动画热闹但业务含义不清”。

## M5：园区、多楼栋与资产优化

改动：

- 室外道路、花园、停车场、无障碍坡道；
- 多楼栋数据驱动生成；
- LOD、纹理压缩、静态合批；
- 模型资产授权清单；
- 性能监控面板仅在开发环境开放。

验收：

- 加楼栋只改数据/清单；
- 手机端保留总览能力；
- 线上首屏体积和 FPS 达标。

## 九、零回归保护

1. **不直接重写现有 `Room3D.vue`**：先新增新运行时，在 feature flag 下逐主题替换；
2. **每阶段独立提交**：M0、M1、M2、M3 不混在一个提交；
3. **保留旧渲染入口**：新场景失败自动退回旧场景；
4. **所有外部模型本地化**：避免跨域、源站失效和授权不清；
5. **数据接口不先改**：人物系统先消费现有 `/api/overview/*`；
6. **回归矩阵**：
   - 10 个路由冒烟；
   - 375 / 768 / 1024 / 1440 四视口；
   - WebGL 开启与失败降级；
   - 鼠标、触控、键盘；
   - 总览、楼层、房间、功能区下钻；
7. **性能对比**：每阶段记录 `renderer.info.render.calls / triangles / frame`；
8. **部署继续使用备份 + 暂存 + 原子切换**。

## 十、推荐的实际执行顺序

## 十一、下一步建议

下一次实施先做 **M0 + M1**，暂时不引入外部人物资产：

1. 移除粒子；
2. 统一总览和特写的相机控制；
3. 给对象聚焦、返回、重置建立明确操作；
4. 做前后截图和性能对比；
5. 验收操作手感后，再确定人物模型的美术风格。

人物模型进入 M3 前，需要单独确认一次美术方向：

- A. 低多边形写实（推荐，稳重、性能好）；
- B. 卡通圆润（亲和，但容易偏儿童化）；
- C. 半写实 PBR（质感最好，但模型体积和移动端压力最大）。

默认建议：**低多边形写实 + 暖色康养空间 + 数据状态叠加**。
